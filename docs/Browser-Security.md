# 浏览器安全策略 (Browser Security Policy)

解决在开放的 Web 环境中，如何防止恶意网站窃取用户隐私数据、滥用用户身份凭证或破坏网站正常功能的问题。浏览器作为用户与互联网交互的唯一入口，内置了一系列核心安全机制。

## 核心原理

- **同源策略 (Same-Origin Policy, SOP)**：浏览器最基础的安全基石。它严格限制了从一个源加载的文档或脚本如何与来自另一个源的资源进行交互。
  - **“同源”的定义**：协议（Protocol）、域名（Domain）和端口（Port）必须完全一致。三者中有任何一个不同，即为跨域。
  - **限制范围**：
    1. 无法读取非同源的 Cookie、LocalStorage 和 IndexedDB。
    2. 无法读取非同源的 DOM（如 iframe 嵌套）。
    3. 拦截向非同源地址发送的 AJAX/Fetch 请求的响应数据。

## 常见的浏览器安全威胁与防御

### 1. XSS (跨站脚本攻击, Cross-Site Scripting)

**原理**：攻击者通过各种手段（如评论区留言、恶意链接参数）将恶意 JavaScript 代码注入到受信任的页面中。当其他用户浏览该页面时，恶意脚本在用户的浏览器中执行，从而窃取 Cookie 或冒充用户进行操作。由于脚本是在同源页面内执行的，因此**同源策略无法防范 XSS**。

**防御结构**：

- **HttpOnly Cookie**：设置 Cookie 的 `HttpOnly` 标志，禁止 JavaScript（如 `document.cookie`）读取该 Cookie，从而切断 XSS 窃取身份凭证的途径。
- **输入转义/输出过滤**：在前端渲染用户输入时，严格进行 HTML 实体转义（避免直接使用 `innerHTML`）。
- **内容安全策略 (CSP, Content Security Policy)**：通过 HTTP 响应头限制浏览器只能加载和执行指定白名单中的脚本。

### 2. CSRF (跨站请求伪造, Cross-Site Request Forgery)

**原理**：攻击者诱导受害者在一个已登录的网站 A 之外，访问恶意网站 B。网站 B 中包含指向网站 A 的请求（如一个隐藏的表单或图片）。因为受害者在 A 网站的会话仍有效，浏览器会自动携带 A 网站的 Cookie 发送请求，从而在受害者不知情的情况下执行了恶意操作（如转账、修改密码）。

**防御结构**：

- **SameSite Cookie**：设置 Cookie 的 `SameSite` 属性为 `Lax` 或 `Strict`，阻止浏览器在跨站请求中携带该 Cookie。
- **CSRF Token**：服务器在渲染页面时下发一个随机 Token，前端在每次请求时通过自定义 Header 或请求体带上该 Token，服务器校验其有效性。
- **验证 Referer/Origin**：服务器校验 HTTP 请求头中的来源地址是否为受信任的站点。

## 技术权衡

**优点：**

- **保护用户**：极大地提高了普通用户上网的安全性，避免了“访问一个恶意网站，所有其他网站账号都被盗”的灾难性后果。

**缺点：**

- **开发复杂度增加**：同源策略严格限制了跨域数据交互，迫使现代前后端分离架构和微服务架构必须引入额外的机制（如 CORS）来“开后门”。

## 关联知识

- **[CORS (跨域资源共享)](./CORS.md)**：为了在同源策略的限制下实现合法的跨域数据交互，而引入的一种服务器端授权机制。
- **Cookie 机制**：XSS 和 CSRF 攻击的核心往往都围绕着 Cookie 的窃取或滥用展开。
